Audience: whoever is doing the ACF work in WP Admin.
Source of truth for requirements: `prideinturfremainingpagetemplatebriefs.md` (Aug 10, 2026).
Baseline audited for this document: `_project/exports/acf-export-corrected.json` (14 field groups).

Nothing here changes site architecture, the coding sheet, the location model, or any content claim.

## How to read this

Work is split into three priorities. **You can stop after Priority 1 and I can still build all four
templates** — Priority 2 items unlock optional sections that will simply not render without them, and
Priority 3 is hygiene that prevents editor mistakes later.

| Priority | What it is | Blocks template build? |
|---|---|---|
| **P1** | The brief's named gaps + the duplicate-group cleanup | Yes — Team Card and Program Card on service pages cannot exist without these |
| **P2** | Fields the section outlines require but the gap list didn't name | No — sections stay hidden until filled |
| **P3** | Corrections to existing fields that violate the brief's heading/data rules | No — but fix before content entry |

Two ways to do the work:

- **Manual (recommended for edits to existing groups).** Every step below gives exact label, name,
  type, and settings. Field *names* are what the templates bind to, so the names must match
  character-for-character. Keys are auto-generated by ACF and don't matter for Bricks binding.
- **Import (recommended for the brand-new group only).** `_project/exports/acf-import-team-members.json`
  is a complete, ready field group. ACF → Tools → Import Field Groups. Zero overwrite risk because
  the group doesn't exist yet. **Do not** try to import edits to existing groups — an ACF import
  replaces a whole group by key, and would wipe anything on your live site that has drifted from the
  repo export.

When you're done, export all field groups (ACF → Tools → Export → Select All → Export As JSON), drop
the file at `_project/exports/acf-export-2026-08-11.json`, and tell me. I'll verify against this list
before writing template JSON.

# Priority 3 — Corrections to existing fields

These are defects in the current export, not new requirements. Each one either contradicts a rule in
the brief or will produce bad data during content entry.

## P3.1 `hero_heading_override` is a WYSIWYG and must not be

Group **Page Hero** (`group_6a24e2a799500`), field `hero_heading_override`, currently type **WYSIWYG**.

The brief's heading system says: *"Do not place a WYSIWYG field directly inside a template-controlled
heading unless the markup is sanitized to inline text."* A WYSIWYG outputs `<p>` tags, so binding it
to an H1 produces `<h1><p>…</p></h1>` — invalid markup that breaks the one-H1 rule the whole heading
system rests on.

**Fix:** change the field type to **Text**. Check the two pages using this group (About 286, Contact
287) plus the homepage for existing content first — changing type keeps the stored value but will
leave any `<p>` wrappers in the string, so clear and re-enter those values as plain text.
